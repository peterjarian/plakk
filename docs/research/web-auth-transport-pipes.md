# Web authentication, backend transport, and Pipes

Research date: 2026-07-26. Desktop parity is the baseline; this note records constraints, not detailed wiring.

## Answer

Web can keep the existing product boundary: AuthKit owns the browser session, while the browser talks directly to the independent Plakk RPC backend with a fresh WorkOS access token. Effect's HTTP RPC transport supports both ordinary calls and the existing streamed invalidation RPC in a browser. No Web-server RPC proxy is required.

WorkOS Pipes must remain behind the Plakk backend. Web can own the user-facing choose/connect/return/reconnect/unlink experience, but the backend must continue deriving the WorkOS user from the authenticated token, holding the WorkOS API key, creating authorization URLs, reading status, and deleting connected accounts.

The one unresolved product constraint is switching or unlinking while Snippets exist. WorkOS deletion removes the stored provider credentials, while Plakk's existing Snippets retain their original provider. They can no longer be downloaded unless that provider is reconnected, and later deletion can remove Plakk metadata without being able to remove the provider object. “Switch provider” therefore needs a separate explicit policy; it is not a free consequence of the current unlink RPC.

## Decision inputs

### Authentication boundary

- The Web scaffold already follows the AuthKit TanStack Start model: server middleware, CSRF middleware, a sign-in endpoint, and a server callback route. AuthKit's current SDK exposes `getAuth()` for server-side session checks and `useAccessToken().getAccessToken()` for a guaranteed-fresh token in browser code. The latter is specifically documented for bearer-authenticated API requests. ([AuthKit TanStack Start README](https://github.com/workos/authkit-tanstack-start/blob/089a3e5acdc14856fb10213b69d7df6331fb46ae/README.md#useaccesstoken), [current Web middleware](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/web/src/start.ts), [current callback](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/web/src/routes/api/auth/callback.tsx))
- After the Web server has authenticated the account, browser RPC calls should use a fresh AuthKit access token as `Authorization: Bearer …`; the token should be treated as ephemeral client state rather than persisted in SQLite or browser storage. WorkOS describes the access token as the JWT a backend validates on each request and keeps refresh-token handling in the secure application session. ([WorkOS sessions](https://workos.com/docs/authkit/sessions), [WorkOS session-token reference](https://workos.com/docs/reference/authkit/session-tokens))
- This matches the existing backend contract. It accepts bearer JWTs, verifies them with the WorkOS JWKS, and derives `CurrentUser.id` from `sub`; protected RPC callers cannot choose another Pipes user ID. ([backend auth middleware](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/backend/src/middleware/AuthMiddlewareLive.ts#L9-L47), [protected RPC group](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/packages/shared/src/api/PlakkApi.ts#L203-L205))

### Direct RPC and invalidation stream

- Effect 4's HTTP RPC protocol sends each RPC as an HTTP `POST`; with framed NDJSON serialization it consumes `response.stream` incrementally. RPC calls and streaming calls create spans by default and place `traceId`, `spanId`, and `sampled` in the encoded RPC request. The server uses those values as the RPC span parent. ([Effect `RpcClient` 4.0.0-beta.92](https://github.com/Effect-TS/effect/blob/effect%404.0.0-beta.92/packages/effect/src/unstable/rpc/RpcClient.ts#L292-L480), [Effect HTTP protocol](https://github.com/Effect-TS/effect/blob/effect%404.0.0-beta.92/packages/effect/src/unstable/rpc/RpcClient.ts#L872-L998), [Effect `RpcServer`](https://github.com/Effect-TS/effect/blob/effect%404.0.0-beta.92/packages/effect/src/unstable/rpc/RpcServer.ts#L95-L135))
- Browser Fetch exposes response bodies as `ReadableStream`, so the existing `WatchSnippetInvalidations` shape is browser-capable. The production path still has to preserve streaming through any hosting proxy/CDN rather than buffer or terminate the response. ([Fetch Standard body mixin](https://fetch.spec.whatwg.org/#body-mixin), [current streamed RPC](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/packages/shared/src/api/PlakkApi.ts#L170-L178))
- Cross-origin access is the actual gap. The backend currently allows only `plakk-app://renderer`; it must also allow the exact deployed Web origins. `Authorization` is explicitly a CORS non-wildcard header, and the RPC content type is not a simple form content type, so browser calls preflight and require `POST`, `authorization`, and `content-type` to be admitted. ([current backend CORS](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/backend/src/main.ts#L46-L55), [Fetch CORS rules](https://fetch.spec.whatwg.org/#cors-protocol))
- A production HTTPS Web page also requires an HTTPS backend; mixed active content cannot be the deployment model. This and stream-preserving hosting are deployment constraints, not reasons to introduce a Web-server proxy.

### Pipes lifecycle

- Google Drive, Dropbox, and Microsoft OneDrive are all first-party Pipes providers with the exact slugs already used by Plakk. ([WorkOS provider list](https://workos.com/docs/pipes/providers), [Plakk provider mapping](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/backend/src/storage/StorageProvider.ts#L121-L130))
- The authorization API is server-authenticated with the WorkOS API key. It accepts the authenticated `user_id`, optional `return_to`, and returns a URL to which the browser is redirected. Web therefore needs a normal full-page redirect and a Web-owned return route that re-reads authoritative status; it does not need to exchange a provider OAuth code itself. The backend should supply a trusted application return URL rather than accept an arbitrary redirect target from the browser. ([WorkOS connected-account authorization](https://workos.com/docs/reference/pipes/connected-account#get-authorization-url), [WorkOS Node v10.7.0 API](https://github.com/workos/workos-node/blob/v10.7.0/src/pipes/pipes.ts#L240-L273), [current Plakk begin-link RPC](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/backend/src/rpcs/StorageRpcsLive.ts#L22-L46))
- Initial connection and reconnection use the same authorization-URL operation. Authoritative states are connected, needs reauthorization, or absent/not installed. Credential vending reports `needs_reauthorization` or `not_installed`, and WorkOS performs OAuth token refresh server-side. Plakk already maps these facts into `CONNECTED`, `NEEDS_REAUTHORIZATION`, and `NOT_CONNECTED`. ([WorkOS Pipes overview](https://workos.com/docs/pipes), [credentials reference](https://workos.com/docs/reference/pipes/access-token), [current Plakk status mapping](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/backend/src/rpcs/StorageRpcsLive.ts#L47-L124))
- Unlink is destructive at the credential boundary: WorkOS removes its stored access and refresh tokens but does not revoke the provider-side grant. Reconnection requires authorization again. Plakk's current unlink operation is idempotent for an already-absent account. ([WorkOS delete connected account](https://workos.com/docs/reference/pipes/connected-account#delete-a-connected-account), [current Plakk unlink RPC](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/backend/src/rpcs/StorageRpcsLive.ts#L125-L141))
- Plakk currently enforces at most one linked provider, but Snippets retain their own provider and downloads vend credentials for that stored provider. This is why unlink/switch semantics must be decided before promising the complete lifecycle. ([single-provider invariant](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/backend/src/storage/StorageProviderLive.ts#L108-L160), [download ownership](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/backend/src/rpcs/SnippetRpcsLive.ts#L187-L220), [best-effort provider deletion](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/backend/src/rpcs/SnippetRpcsLive.ts#L223-L255))

### Trace continuity and Axiom

- Cross-client/backend trace continuity is supported without inventing a second correlation protocol: Effect RPC already propagates its span identity inside the RPC envelope. Effect's HTTP client can additionally emit W3C `traceparent` and B3 headers, while its HTTP server tracer can read them. If that HTTP-level propagation is enabled for browser requests, the corresponding headers must be included in backend CORS. ([Effect trace-context source](https://github.com/Effect-TS/effect/blob/effect%404.0.0-beta.92/packages/effect/src/unstable/http/HttpTraceContext.ts), [W3C Trace Context](https://www.w3.org/TR/trace-context/))
- The backend already exports OTLP telemetry when configured. Axiom accepts OTLP/HTTP traces, logs, and metrics using an ingestion token and dataset header. A browser bundle cannot keep that token secret, so Web telemetry needs a trusted ingestion boundary; the exact collector/export path is an implementation choice and need not be fixed by this plan. ([current backend telemetry](https://github.com/peterjarian/plakk/blob/db0e819aefb123e5426e23e0ceb5a6e80c17a66e/apps/backend/src/TelemetryLive.ts), [Axiom OpenTelemetry ingestion](https://axiom.co/docs/send-data/opentelemetry))

## Resulting direction

Adopt direct, bearer-authenticated browser RPC and the existing invalidation stream; expand backend CORS for known Web origins; keep all WorkOS API-key and Pipes credential operations in the backend; return from Pipes authorization to a Web-owned route and refresh status; preserve the current three-state storage model and Desktop behavior. Resolve the existing-Snippet policy before specifying unlink and provider switching.
